## 三、背景技术

### 3.1 现有技术现状

在移动互联网应用开发中，通常存在以下几类终端形态：
- **小程序**：微信小程序、支付宝小程序等
- **H5 应用**：基于浏览器的移动端网页
- **原生 App**：iOS/Android 原生应用

同时，大多数商业应用都配备有管理后台系统，用于配置应用的各类参数（如品牌设置、首页布局、活动配置等）。

### 3.2 现有技术的问题

目前，管理后台与终端应用的开发和预览存在以下痛点：

**问题一：多端独立开发，周期长、成本高（核心痛点）**

传统的开发模式是小程序、iOS App、Android App 各自独立开发：

```
传统开发模式示意:
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  小程序团队   │    │   iOS 团队   │    │ Android 团队 │
│  独立开发     │    │  独立开发    │    │  独立开发    │
│  独立测试     │    │  独立测试    │    │  独立测试    │
│  独立发版     │    │  独立发版    │    │  独立发版    │
└──────────────┘    └──────────────┘    └──────────────┘
        │                  │                   │
        └──────────────────┼───────────────────┘
                           ▼
            新增一个终端（如从小程序复刻出 App）
                    需要 3-6 个月
```

- 新增一个终端（例如从小程序复刻出 App）通常需要 **3-6 个月**
- 各端代码无法复用，相同功能需要重复开发
- 各端表现可能不一致，用户体验难以保证

**问题二：配置修改流程繁琐，需多团队协调**

```
传统配置修改流程:
后台修改 → 通知小程序团队 → 修改 → 打包 → 审核 → 发版
          → 通知 iOS 团队    → 修改 → 打包 → 审核 → 发版
          → 通知 Android 团队 → 修改 → 打包 → 审核 → 发版

周期: 3-7 天（需要协调四个团队）
```

- 例如运营修改"双十一促销横幅"，需要通知四个团队分别修改并排期
- 配置修改无法实时生效，错过最佳时机

**问题三：预览与真实终端分离**
- 管理人员在后台配置完成后，需要切换到真实终端（手机/模拟器）查看效果
- 配置修改后无法实时看到终端呈现效果
- 预览效率低，配置调整周期长

**问题四：多身份场景难以预览**
- 现代应用常存在多种用户身份（如普通用户、服务提供者）
- 不同身份看到的界面、功能入口、数据完全不同
- 现有技术难以在同一预览环境中快速切换身份视角

**问题五：跨平台代码重复开发**
- 小程序和 Web 端需要分别开发预览组件
- 代码无法复用，维护成本高
- 界面表现可能不一致

**问题六：权限安全边界模糊**
- 预览模式与真实模式的权限边界不清
- 可能导致越权访问或数据泄露风险
- 缺乏统一的安全护栏机制

### 3.3 现有解决方案的局限性

**预览方案对比：**

| 现有方案 | 局限性 |
|---------|--------|
| 真机预览 | 需要真实设备，效率低，无法实时同步 |
| 模拟器预览 | 无法与后台配置联动，身份切换困难 |
| iframe 嵌入 | 跨域限制，样式隔离困难，无法模拟原生能力 |
| 截图预览 | 静态呈现，无交互能力，无法验证业务逻辑 |

**多端开发方案对比：**

| 现有方案 | 周期 | 复用率 | 局限性 |
|---------|------|--------|--------|
| 各端独立开发 | 3-6 月 | 0% | 重复开发、不一致、人力成本高 |
| 跨端框架（Flutter/RN） | 1-2 月 | 60-80% | 仍需处理各端差异、调试困难 |
| 微前端/H5 容器 | 2-4 周 | 70-90% | 性能损耗、原生能力受限 |
| **本发明** | **3-5 天** | **95%+** | **统一内核+换壳，配置即生效** |

## 四、发明内容

### 4.1 核心设计理念：从"多端独立开发"到"统一模型配置"

本发明的核心创新在于**将传统的"多端独立开发"模式转变为"统一模型配置"模式**，把"做多个产品"变成了"做一个产品"，从而实现开发周期的极致压缩。

#### 4.1.1 "万能底盘"架构比喻

可以用汽车制造来理解本发明的核心理念：

| 传统做法 | 本发明做法 |
|---------|-----------|
| 像分别造一辆轿车、一辆 SUV 和一辆卡车，每辆车都要从头造起 | 造一个**"万能底盘"**，只需要根据需求换上不同的外壳，就能瞬间变成不同的车 |
| 新增一个终端（如从小程序复刻出 App）需要 3-6 个月 | 复刻终端周期从数月压缩到 **3-5 天**，人力成本几乎降为零 |

- **配置驱动**：后台配置被视为所有终端的"单一真源"（Single Source of Truth）
- **换壳复制**：新增终端不再是重新开发，而是复用已有核心功能，只换"外壳"并对接少量原生功能

- **页面级复用（非截图）**：预览器直接挂载真实的终端页面组件，复用真实的路由和参数规范
- **真实数据与权限验证**：预览器运行真实的业务数据，支持模拟不同身份（普通用户、VIP、员工）的权限逻辑
- **即时生效**：运营修改配置后，所有终端自动同步，无需通知多个团队分别修改

#### 4.1.3 本质：将软件工程问题降维为配置问题

本发明之所以能将数月的开发周期压缩至几天，本质上是因为：

> **把"新增终端"从一个繁重的软件工程问题，降维成了一个简单的系统配置问题。**

### 4.2 要解决的技术问题

本发明要解决的技术问题是：
1. 如何在管理后台中实时预览终端界面，且配置修改能即时反映
2. 如何在单一预览环境中支持多身份视角的快速切换
3. 如何实现预览组件在 Web 和小程序环境下的代码复用
4. 如何确保预览模式与真实模式的安全隔离
5. **如何将多端独立开发模式转变为统一模型配置模式，极致压缩开发周期**

#### 4.3.2 双会话模型

本发明的核心创新之一是**双会话模型**，用于支持同一终端内多身份的共存与切换：

```
┌─────────────────────────────────────────────────────────────┐
│                      会话存储层                              │
├────────────────────────┬────────────────────────────────────┤
│      用户会话          │         服务提供者会话             │
│   (UserSession)        │       (EscortSession)              │
├────────────────────────┼────────────────────────────────────┤
│ Token Key:             │ Token Key:                         │
│ terminalPreview.       │ terminalPreview.                   │
│ userToken              │ escortToken                        │
├────────────────────────┼────────────────────────────────────┤
│ 适用场景:              │ 适用场景:                          │
│ - 浏览服务             │ - 工作台                           │
│ - 下单支付             │ - 接单管理                         │
│ - 营销活动             │ - 收入提现                         │
│ - 个人中心             │ - 分销中心                         │
└────────────────────────┴────────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────────┐
│                    视角推导引擎                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  输入: escortToken 存在性 + 验证结果                        │
│                                                             │
│  推导规则:                                                  │
│  ┌─────────────────────────────────────────────────────┐    │
│  │ IF escortToken 存在 AND 验证有效 THEN               │    │
│  │     effectiveViewerRole = 'escort'                  │    │
│  │ ELSE                                                 │    │
│  │     effectiveViewerRole = 'user'                    │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                             │
│  输出: effectiveViewerRole ('user' | 'escort')             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**双会话模型的关键特征**：

1. **会话独立存储**：用户会话和服务提供者会话使用不同的存储 Key，互不干扰
2. **会话可并存**：同一用户可同时持有两种身份的会话凭证
3. **视角动态推导**：当前展示的视角由服务提供者会话的有效性决定
4. **无缝切换**：切换视角无需重新登录，只需切换活跃会话

#### 4.3.4 跨平台适配架构

本发明采用**三层抽象架构**实现跨平台代码复用：

#### 4.3.5 能力桥接层（WxBridge）

本发明设计了统一的**能力桥接接口**，实现原生能力的抽象：

```typescript
// 桥接接口定义
interface WxBridge {
  // 登录能力
  login(): Promise<LoginResult>
  checkSession(): Promise<boolean>
  
  // 支付能力
  requestPayment(params: PayParams): Promise<PayResult>
  
  // 分享能力
  share(params: ShareParams): void
  getShareParams(): ShareParams | null
  
  // 媒体能力
  chooseImage(params?: ChooseImageParams): Promise<ImageResult>
  uploadFile(params: UploadParams): Promise<UploadResult>
  previewImage(urls: string[], current?: string): void
  
  // 定位能力
  getLocation(params?: LocationParams): Promise<LocationResult>
  
  // 扫码能力
  scanCode(params?: ScanParams): Promise<ScanResult>
  
  // 存储能力
  storage: StorageAdapter
  
  // 导航能力
  navigateTo(url: string): void
  redirectTo(url: string): void
  navigateBack(delta?: number): void
  
  // 提示能力
  showToast(params: ToastParams): void
  showLoading(title: string): void
  hideLoading(): void
  showModal(params: ModalParams): Promise<ModalResult>
}
```

**桥接实现策略**：

| 运行环境 | 实现方式 | 说明 |
|---------|---------|------|
| Web 预览 | mockWxBridge | 模拟实现，支付用 confirm 模拟 |
| 小程序 | realWxBridge | 真实调用 wx.* API |

#### 4.3.6 安全隔离机制

本发明设计了严格的**安全隔离机制**，确保预览模式不会影响真实环境：

```
┌─────────────────────────────────────────────────────────────┐
│                    安全护栏体系                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. Token 隔离                                              │
│  ┌─────────────────────────────────────────────────────┐    │
│  │ 预览器 Token:   terminalPreview.userToken           │    │
│  │ 真实端 Token:   kekeling_userToken                  │    │
│  │ → 两套 Token 存储空间完全隔离                        │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                             │
│  2. Mock Token 识别                                         │
│  ┌─────────────────────────────────────────────────────┐    │
│  │ 规则: Token 以 'mock-' 开头                         │    │
│  │ 行为: 直接返回 Mock 数据，不请求真实后端            │    │
│  │ 目的: 避免 Mock 数据污染真实数据库                  │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                             │
│  3. DebugPanel 访问控制                                     │
│  ┌─────────────────────────────────────────────────────┐    │
│  │ 显示条件: process.env.NODE_ENV === 'development'    │    │
│  │         AND isPreviewMode === true                  │    │
│  │ → 真实终端永远不显示调试面板                        │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                             │
│  4. 视角切换约束                                            │
│  ┌─────────────────────────────────────────────────────┐    │
│  │ 预览器: 允许通过 Props 强制指定 viewerRole          │    │
│  │ 真实端: viewerRole 只能由 token 验证结果推导        │    │
│  │ → 禁止将预览器的视角切换逻辑搬到真实端              │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                             │
│  5. 通道强制规则                                            │
│  ┌─────────────────────────────────────────────────────┐    │
│  │ /escort-app/* 路径必须使用 escortRequest 通道       │    │
│  │ 违反时抛出 ChannelMismatchError                     │    │
│  │ → 防止越权访问服务提供者专属接口                    │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 六、权利要求书要点

### 6.1 独立权利要求

**权利要求 1**：一种基于双会话模型的跨平台终端行为模拟系统，其特征在于，包括：

- **会话管理模块**：用于管理用户会话和服务提供者会话，两种会话独立存储、可并存；
- **视角推导引擎**：基于服务提供者会话的有效性推导当前视角角色；
- **数据通道分发器**：根据接口路由规则选择对应的请求通道，并自动附加身份凭证；
- **平台适配层**：提供统一的请求、存储、原生能力抽象接口，屏蔽宿主环境差异；
- **页面渲染引擎**：根据当前页面 Key 和视角角色渲染对应的页面组件。

**权利要求 2**：一种基于双会话模型的终端行为模拟方法，其特征在于，包括以下步骤：

- S1：初始化预览器组件，检测运行环境并选择对应的平台适配实现；
- S2：读取本地存储的用户会话和服务提供者会话凭证；
- S3：基于服务提供者会话凭证的有效性推导当前视角角色；
- S4：根据当前页面类型和视角角色加载对应的数据；
- S5：渲染页面组件，根据视角角色控制功能入口和数据展示。

### 6.2 从属权利要求

**权利要求 3**：根据权利要求 1 所述的系统，其特征在于，所述数据通道分发器包括：

- 用户通道，用于发送用户端接口请求，自动携带用户会话凭证；
- 服务提供者通道，用于发送服务提供者专属接口请求，自动携带服务提供者会话凭证；
- 通道选择器，根据接口路径前缀选择对应通道。

**权利要求 4**：根据权利要求 1 所述的系统，其特征在于，所述系统还包括 Mock 降级处理器，当满足以下条件之一时返回 Mock 数据：

- 会话凭证以预设的模拟标识开头；
- 接口返回特定错误状态码；
- 网络请求发生异常。

**权利要求 5**：根据权利要求 1 所述的系统，其特征在于，所述平台适配层包括能力桥接器，提供统一的支付、分享、媒体选择、定位、扫码等原生能力抽象接口，在 Web 环境下使用模拟实现，在小程序环境下使用真实原生 API 实现。

**权利要求 6**：根据权利要求 2 所述的方法，其特征在于，所述步骤 S3 中，视角推导规则为：若服务提供者会话凭证存在且验证有效，则视角角色为服务提供者；否则为普通用户。

**权利要求 7**：根据权利要求 1 所述的系统，其特征在于，所述系统还包括实时数据覆盖模块，支持管理后台的配置数据实时覆盖预览器显示，数据优先级从高到低依次为：Props 覆盖数据、API 返回数据、默认值。

**权利要求 8**：根据权利要求 1 所述的系统，其特征在于，所述系统还包括安全隔离模块，实现以下安全机制：

- 预览器会话凭证与真实终端会话凭证使用不同的存储 Key；
- 模拟凭证不触发真实后端数据变更；
- 调试面板仅在开发环境且预览模式下显示；
- 视角切换能力仅限预览器使用，真实终端的视角由凭证验证结果推导。
