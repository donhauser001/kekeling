## 三、🔴 P0 安全问题（必须立刻改）

### 3.1 前端 XSS 注入面（dangerouslySetInnerHTML/innerHTML）

**风险等级**：🔴 Critical

**发现的注入点**：

| # | 文件 | 行号 | 模式 | 数据来源 |
|---|------|------|------|----------|
| 1 | `operation-guides-detail-sheet.tsx` | 98 | `dangerouslySetInnerHTML={{ __html: item.content }}` | 运营指南内容 |
| 2 | `ServiceDetailPage.tsx` | 666 | `dangerouslySetInnerHTML={{ __html: service.content }}` | 服务详情富文本 |
| 3 | `ContentSection.tsx` | 28 | `dangerouslySetInnerHTML={{ __html: homeSettings.content.code }}` | 首页配置内容 |
| 4 | `rich-editor/index.tsx` | 106 | `editorRef.current.innerHTML = value` | 富文本编辑器 |
| 5 | `rich-editor/index.tsx` | 125 | `editorRef.current.innerHTML = ''` | 富文本编辑器 |

**风险判定**：
- 只要数据来源存在"用户输入 / 富文本 / 运营粘贴 / 后端下发 / 第三方接口"中任一种，即构成可利用注入点
- 一旦 XSS 成功，结合当前 token 存储方式（localStorage），攻击者可直接窃取会话凭证

**整改方案（强制）**：

```typescript
// ✅ 方案一：使用 DOMPurify 净化（推荐）
import DOMPurify from 'dompurify'

// 创建统一的 SafeHTML 组件
function SafeHTML({ html, className }: { html: string; className?: string }) {
  const sanitized = DOMPurify.sanitize(html, {
    ALLOWED_TAGS: ['p', 'br', 'strong', 'em', 'ul', 'ol', 'li', 'h1', 'h2', 'h3', 'a', 'img'],
    ALLOWED_ATTR: ['href', 'src', 'alt', 'class'],
    FORBID_TAGS: ['style', 'script', 'iframe', 'svg', 'math'],
    FORBID_ATTR: ['onerror', 'onclick', 'onload', 'style']
  })
  return <div className={className} dangerouslySetInnerHTML={{ __html: sanitized }} />
}

// ✅ 方案二：后端转结构化 blocks（更安全）
// 后端将富文本转成 JSON blocks，前端只渲染受控组件
interface ContentBlock {
  type: 'paragraph' | 'heading' | 'list' | 'image'
  content: string
  level?: number
}
```

**验收标准**：
- [ ] 全仓搜索 `dangerouslySetInnerHTML` 只出现在 `SafeHTML` 组件内
- [ ] `SafeHTML` 组件强制 DOMPurify 净化
- [ ] ESLint 规则禁止直接使用 `dangerouslySetInnerHTML`

### 3.2 会话凭证存储不安全

**风险等级**：🟠 High

**当前存储方式**：

| 位置 | 方式 | 问题 |
|------|------|------|
| `session.ts:75,83,99,107` | `localStorage.setItem/getItem` | JS 可读，XSS 可窃取 |
| `cookies.ts:33,42` | `document.cookie` | 非 HttpOnly，JS 可读 |
| `sidebar.tsx:83` | `document.cookie` | 非 HttpOnly |

**风险判定**：
- 一旦出现任何 XSS（当前确实存在多个注入面），token 会被直接读走
- CSRF 风险随之上升

**整改方案**：

| 优先级 | 方案 | 说明 |
|--------|------|------|
| P0 止血 | Token 内存态 | 刷新后重新登录，localStorage 不存完整 token |
| P1 正解 | HttpOnly Cookie | 后端下发 `HttpOnly; Secure; SameSite=Lax` cookie |

```typescript
// ❌ 当前危险模式
localStorage.setItem(TOKEN_KEY, token)

// ✅ P0 止血：只放内存
let memoryToken: string | null = null
export const setToken = (token: string) => { memoryToken = token }
export const getToken = () => memoryToken

// ✅ P1 正解：后端设置 HttpOnly cookie
// Set-Cookie: session=xxx; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800
```

### 3.3 终端预览器属于"高危渲染器"

**风险等级**：🟠 High

**问题**：终端预览器本质是"动态内容展示器"，如果它把日志、富文本、HTML 片段、错误堆栈直接拼进 DOM，会成为**全站最大的注入入口**。

**特殊风险点**：
- `ServiceDetailPage.tsx` 中的 `service.content` 渲染
- `ContentSection.tsx` 中的 `homeSettings.content.code` 渲染
- 任何"复制粘贴的内容"都必须当作不可信输入

**整改建议**：
- 预览器默认仅渲染纯文本（`textContent`）
- 需要高亮时用受控渲染（如 ANSI to HTML 必须净化）
- 所有外部内容强制走 `SafeHTML` 组件

## 四、双身份体系安全加固（重点）

### 4.1 Token 存储安全：渐进式加固路径

**当前状态**：localStorage 存储存在 XSS 风险

**加固路线图**：

#### 阶段一：前端减灾（立即可做）

| 措施 | 说明 | 验收标准 |
|------|------|----------|
| CSP 严格化 | 禁止 inline script，减少 XSS 成功概率 | `Content-Security-Policy` header 生效 |
| Token 内存态 | 刷新丢失（牺牲 UX 换安全） | localStorage 不存完整 token |
| XSS 防护增强 | 输入输出转义、DOMPurify | 安全扫描无 XSS 告警 |

#### 阶段二：正解方案（中期目标）

| 措施 | 说明 | 验收标准 |
|------|------|----------|
| httpOnly Cookie | session/refresh token 走 cookie | 前端 JS 无法读取 token |
| Secure + SameSite | 防 CSRF、仅 HTTPS 传输 | cookie 属性正确设置 |
| Token 分域隔离 | escortToken 与 userToken 分路径 | 互不污染、互不可见 |

### 4.2 Session 失效联动：前后端双重保障

**当前策略**：UserSession 失效时联动清除 EscortSession ✅

**加固要求**：

| 层级 | 要求 | 验收标准 |
|------|------|----------|
| 前端 | userToken 失效时清除 escortToken | `clearEscortToken()` 被调用 |
| 后端 | userToken 注销时使 escortToken 失效 | escort 接口返回 401 |
| 后端 | escortToken 续期依赖 userToken 有效性 | 无法单独续期 |

**后端验收测试用例**：

```typescript
// e2e/auth.spec.ts
describe('Session 联动失效', () => {
  it('userToken 注销后，escortToken 应失效', async () => {
    // 1. 用户登录，获取 userToken
    // 2. 陪诊员登录，获取 escortToken
    // 3. 用户注销（使 userToken 失效）
    // 4. 用 escortToken 访问 escort 接口
    // 5. 期望返回 401
  })
})
```

### 8.1 🔴 Critical：生产 docker-compose.yml 默认口令与默认 JWT_SECRET

**文件**：`docker-compose.yml`

**发现的高危默认值**：

```yaml
# ❌ 这些默认值在公网环境极易被扫到并直接打穿
POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-kekeling123}
JWT_SECRET: ${JWT_SECRET:-kekeling-jwt-secret-key-production-2024}
ports:
  - "${POSTGRES_PORT:-5436}:5432"  # DB 端口暴露到宿主机
  - "${ADMINER_PORT:-8080}:8080"   # Adminer 暴露（profiles=tools）
```

**风险判定**：
- 这属于"扫描器最喜欢的配置"
- 默认 JWT_SECRET 一旦泄露或被猜到，所有 JWT 都可被伪造
- DB 端口暴露 + 弱口令 = 撞库/爆破风险
- Adminer 对公网开放 = 数据库操作台直送攻击者

**整改门槛（强制）**：

| 要求 | 说明 |
|------|------|
| 禁止默认口令/密钥 | 用 `.env` 注入，CI/CD 强制校验"空值不允许启动" |
| DB 不做 ports 映射 | 生产只允许容器网络内部访问 |
| Adminer 限制 | 只允许本地 profile 或绑定 127.0.0.1 + 反向代理鉴权 |
| JWT_SECRET 高熵 | 至少 32 bytes 随机，定期轮换 |

**验收标准**：
- [ ] docker-compose.yml 中无任何默认口令/密钥
- [ ] 生产环境 DB 端口不暴露到宿主机
- [ ] Adminer 生产环境不启用或强制鉴权
- [ ] JWT_SECRET 长度 ≥ 32 字符，随机生成

### 8.2 🔴 Critical：JWT 密钥硬编码（代码层面）

**文件**：`server/src/modules/auth/strategies/jwt.strategy.ts:16`

**影响终端预览器**：✅ 是 - escortToken 验证依赖 JWT

**典型后果**：攻击者可伪造任意身份 token，直接变成"全系统后门"。

| 项目 | 要求 |
|------|------|
| 整改门槛 | 密钥必须来自环境变量或 KMS/Secrets Manager，禁止任何形式硬编码与默认值回退 |
| 密钥轮转 | 上线/测试/开发环境都要换（曾提交到仓库的密钥视为已泄露） |

**验收标准**：
- [ ] 仓库全局搜索不到 `JWT_SECRET` / `secret` 常量明文
- [ ] 线上旧 token 全部失效（强制 re-login）
- [ ] 缺失环境变量时应用启动失败（而非使用默认值）

### 8.2 🟠 High：Upload 接口无鉴权（必须立刻加闸）

**影响终端预览器**：❌ 否 - 预览器不涉及上传（但项目整体风险）

**典型后果**：未授权上传、任意文件写入、恶意脚本载荷、对象存储刷量、间接 RCE

| 项目 | 要求 |
|------|------|
| 整改门槛 | 上传必须带鉴权 + RBAC（谁能上传到哪个业务对象） |
| 文件校验 | 类型白名单 + MIME sniff + 大小限制 + 频率限制 |
| 最佳实践 | 对象存储采用短期预签名直传，后端只签发策略并落库 |

**验收标准**：
- [ ] 未携带合法 token 的上传请求一律 401/403
- [ ] 上传记录可追溯到 userId/escortId、业务对象、IP、UA

### 8.3 🟠 High：支付 Mock 代码残留（必须清仓）

**影响终端预览器**：❌ 否 - 预览器不涉及支付（但项目整体风险）

**典型后果**：绕过真实支付校验、伪造成功回调、产生"0 元购"，直接财务风险

| 项目 | 要求 |
|------|------|
| 整改门槛 | mock 支付逻辑只能存在于 `__tests__` 或 dev-only 路径 |
| 环境隔离 | 生产编译时剔除 mock 分支（环境变量强制关闭） |
| 状态推进 | 订单状态只能由支付网关回调签名验证后推进 |

**验收标准**：
- [ ] 生产环境构建产物中不存在 mock 支付分支（grep 扫描验证）
- [ ] 客户端"支付成功"通知不作为事实来源
