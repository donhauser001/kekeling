### 2.1 API 路径不匹配

**问题描述**
- 前端调用 `/marketing/coupons/my`
- 后端实际路由是 `/coupons/my`
- 导致 404 错误

**⚠️ 失败信号**
```
GET https://kkl.top/api/marketing/coupons/my 404 (Not Found)
```

**解决方案**
```typescript
// ❌ 错误
return await userRequest('/marketing/coupons/my')

// ✅ 正确
return await userRequest('/coupons/my')
```

**预防措施**
- 开发前先确认后端 API 路由（查看 Swagger 文档 `/api/docs`）
- 前后端约定统一的路由命名规范

---

### 2.2 后端认证缺失导致数据不完整

**问题描述**
- `/coupons/available` 接口缺少 `@UseGuards(JwtAuthGuard)`
- 即使请求带了 token，后端也无法获取用户 ID
- 导致 `claimedCount` 始终为 0

**⚠️ 失败信号**
```javascript
// API 返回的数据中，用户相关字段始终为初始值
{ canClaim: true, claimedCount: 0 }  // 即使用户已领取
```

**解决方案**
```typescript
// ❌ 错误：缺少认证守卫
@Get('available')
@ApiOperation({ summary: '获取可领取的优惠券列表' })
async getAvailableTemplates(
  @CurrentUser('sub') userId: string | undefined,  // 始终是 undefined
) { ... }

// ✅ 正确：添加认证守卫
@Get('available')
@UseGuards(JwtAuthGuard)
@ApiBearerAuth()
@ApiOperation({ summary: '获取可领取的优惠券列表' })
async getAvailableTemplates(
  @CurrentUser('sub') userId: string,  // 正确获取用户 ID
) { ... }
```

**经验总结**
- 需要用户身份的接口**必须**添加 `@UseGuards(JwtAuthGuard)`
- 同时添加 `@ApiBearerAuth()` 以便 Swagger 文档正确显示认证需求

### 2.3 错误消息未正确显示

**问题描述**
- 后端返回 `{ message: "领取过于频繁，请稍后再试", statusCode: 400 }`
- 前端只显示 "HTTP 400" 或 "领取失败"
- 用户无法了解真正的错误原因

**⚠️ 失败信号**
```
用户看到：领取失败
实际原因：领取过于频繁，请稍后再试（被吞噬了）
```

**解决方案**

修改 `request.ts` 中的全局错误处理：

```typescript
// ❌ 错误：直接使用状态码
throw new ApiError(response.status, `HTTP ${response.status}`, endpoint)

// ✅ 正确：解析响应体获取实际错误消息
if (!response.ok) {
  let errorMessage = `HTTP ${response.status}`
  try {
    const errorBody = await response.json() as { message?: string; error?: string }
    errorMessage = errorBody.message || errorBody.error || errorMessage
  } catch {
    // JSON 解析失败，使用默认消息
  }
  throw new ApiError(response.status, errorMessage, endpoint)
}
```

**经验总结**
- 错误处理应该是**全局的**，在 request 层统一处理
- `message` 字段才是用户应该看到的内容

### 2.4 POST 请求缺少 Content-Type

**问题描述**
- POST 请求体是 JSON 但未设置 Content-Type
- 后端无法正确解析请求体
- 返回 400 Bad Request

**⚠️ 失败信号**
```
POST /api/coupons/claim 400 (Bad Request)
后端日志：Cannot read property 'templateId' of undefined
```

**解决方案**
```typescript
// ❌ 错误：缺少 Content-Type
await userRequest('/coupons/claim', {
  method: 'POST',
  body: JSON.stringify({ templateId }),
})

// ✅ 正确：添加 Content-Type
await userRequest('/coupons/claim', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({ templateId }),
})
```

**经验总结**
- 所有 POST/PUT/PATCH 请求都应设置 `Content-Type: application/json`
- 可以考虑在 request 层自动添加此 header

### 2.5 数据格式转换

**问题描述**
- 后端返回的字段名与前端期望不一致
- 例如后端返回 `value`，前端期望 `amount`

**⚠️ 失败信号**
```javascript
// 组件中出现 undefined
<Text>¥{coupon.amount}</Text>  // 显示 ¥undefined
// 因为后端返回的是 coupon.value
```

**解决方案**

在 API 层统一进行数据转换（而非在组件层）：

```typescript
// user-api.ts
export const getAvailableCoupons = async (): Promise<AvailableCoupon[]> => {
  const response = await userRequest<BackendCouponTemplate[]>('/coupons/available')
  
  // 在 API 层转换为前端格式
  return response.map(item => ({
    id: item.id,
    name: item.name,
    description: item.description,
    amount: item.value,           // 后端 value → 前端 amount
    minAmount: item.minAmount,
    remaining: item.totalQuantity 
      ? Math.max(0, item.totalQuantity - item.claimedCount) 
      : 999,
    canClaim: item.canClaim,
    claimedCount: item.claimedCount,
    perUserLimit: item.perUserLimit,
  }))
}
```

**最佳实践**
- ✅ 在 API 层（`user-api.ts`）进行数据转换
- ✅ 组件层只使用前端定义的数据结构
- ✅ 在 `types.ts` 中定义清晰的接口类型
- ❌ 不要在组件中做字段映射

**价值**
- 解耦前后端字段变动
- UI 层代码更像业务代码，而非对接代码
- 后续引入 BFF / Mock 都很方便

### 2.6 UI 状态集中判断

**问题描述**
- 需要区分多种状态：已领完、已领取、可领取、领取中
- 状态判断逻辑散落在 JSX 各处，难以维护

**⚠️ 失败信号**
```jsx
// JSX 中到处都是条件判断，难以理清逻辑
<Button disabled={coupon.remaining === 0 || isClaiming || 
  coupon.claimedCount >= coupon.perUserLimit || justClaimed}>
  {coupon.remaining === 0 ? '已领完' : 
   coupon.claimedCount >= coupon.perUserLimit ? '已领取' : 
   isClaiming ? '领取中...' : '立即领取'}
</Button>
```

**解决方案**

把"状态机"从 JSX 中抽出来，集中定义状态判断逻辑：

```typescript
function AvailableCouponCard({ coupon, ... }) {
  const [isClaiming, setIsClaiming] = useState(false)
  const [justClaimed, setJustClaimed] = useState(false)

  // ========== 状态判断（集中定义） ==========
  const isSoldOut = coupon.remaining === 0                      // 总量已领完
  const isUserLimitReached = !coupon.canClaim && 
    coupon.claimedCount >= coupon.perUserLimit                  // 用户达到限领上限
  const isAlreadyClaimed = isUserLimitReached || justClaimed    // 已领取
  const cannotClaim = isSoldOut || isAlreadyClaimed || isClaiming  // 无法领取

  // ========== 派生状态（基于上述判断） ==========
  const getButtonText = () => {
    if (justClaimed) return '已领取'
    if (isClaiming) return '领取中...'
    if (isSoldOut) return '已领完'
    if (isUserLimitReached) return '已领取'
    return '立即领取'
  }

  const getButtonBgColor = () => {
    if (justClaimed || isAlreadyClaimed) return '#10b981'  // 绿色表示已完成
    return primaryColor
  }

  // ========== JSX 变得简洁 ==========
  return (
    <Button
      disabled={cannotClaim}
      onClick={handleClaim}
      style={{ backgroundColor: getButtonBgColor() }}
    >
      <Text>{getButtonText()}</Text>
    </Button>
  )
}
```

**进阶：使用类型定义状态**

```typescript
type CouponUIState = 'sold_out' | 'already_claimed' | 'claiming' | 'available'

const getUIState = (coupon, isClaiming, justClaimed): CouponUIState => {
  if (coupon.remaining === 0) return 'sold_out'
  if (!coupon.canClaim || justClaimed) return 'already_claimed'
  if (isClaiming) return 'claiming'
  return 'available'
}
```

### 2.8 服务器配置问题

**问题描述**
- 后端启用了 HTTPS（自签名证书）
- Nginx 配置为 HTTP 代理
- 导致 502 Bad Gateway

**⚠️ 失败信号**
```html
<html>
<head><title>502 Bad Gateway</title></head>
<body>
<center><h1>502 Bad Gateway</h1></center>
</body>
</html>
```

**解决方案**
```bash
# 检查后端协议
pm2 logs kekeling-api --lines 5 | grep -E "http|https"
# 输出：🚀 科科灵 API 服务已启动: https://0.0.0.0:3000

# 修改 Nginx 配置匹配后端协议
sed -i 's|proxy_pass http://127.0.0.1:3000|proxy_pass https://127.0.0.1:3000|g' \
  /etc/nginx/conf.d/kekeling.conf
nginx -t && systemctl reload nginx
```

**经验总结**
- 部署后端后检查 Nginx 代理协议是否匹配
- 502 错误优先检查 Nginx → 后端的连接

## 3. 改造检查清单

> 每个检查项后的⚠️是"失败信号"，帮助快速定位问题。

### 3.1 后端检查

- [ ] API 路由是否与前端调用一致  
  ⚠️ 404 错误
- [ ] 需要用户身份的接口是否添加了 `@UseGuards(JwtAuthGuard)`  
  ⚠️ 用户相关字段始终为 0 或 null
- [ ] 是否添加了 `@ApiBearerAuth()` 供 Swagger 文档使用
- [ ] 错误消息是否清晰明确（返回 message 字段）
- [ ] 是否有必要的防刷/限流机制

### 3.2 前端 API 层检查

- [ ] API 路径是否正确（参照 Swagger 文档 `/api/docs`）  
  ⚠️ 404 错误
- [ ] POST/PUT 请求是否设置了 `Content-Type: application/json`  
  ⚠️ 400 Bad Request
- [ ] 是否在 API 层进行了数据格式转换  
  ⚠️ 组件中出现 undefined
- [ ] 错误处理是否解析了后端返回的实际错误消息  
  ⚠️ 只显示 "HTTP 400"
- [ ] 接口类型定义是否完整

### 3.3 前端组件层检查

- [ ] 是否正确使用后端返回的状态字段（canClaim, claimedCount 等）
- [ ] UI 状态是否有集中的判断逻辑（不散落在 JSX 中）
- [ ] 加载状态、错误状态、空状态是否都有处理
- [ ] 操作按钮是否有 loading 和 disabled 状态
- [ ] 用户反馈（Toast）是否清晰

### 3.4 跨平台兼容检查

- [ ] 使用的组件是否都在 `primitives` 中导出  
  ⚠️ 编译警告 "was not found"
- [ ] 是否使用 `wxScale` 处理尺寸
- [ ] 事件处理是否使用 `onChange` 而非 `onInput`
- [ ] 导航栏是否符合规范（参照小程序页面改造规范）

### 3.5 部署检查

- [ ] Nginx 代理协议是否与后端一致（HTTP/HTTPS）  
  ⚠️ 502 Bad Gateway
- [ ] 服务是否正常启动  
  ⚠️ pm2 list 显示 errored

## 4. 代码模板

### 4.1 API 函数模板（含数据转换和错误处理）

```typescript
/**
 * [功能描述]
 * 接口: [METHOD] [PATH]
 * 通道: userRequest
 */
export const fetchSomething = async (
  params: RequestParams
): Promise<{ success: boolean; data?: ResponseData; message?: string }> => {
  try {
    const response = await userRequest<BackendResponse>('/path', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
      },
      body: JSON.stringify(params),
    })
    
    // 数据转换：后端格式 → 前端格式
    const data = transformToFrontendFormat(response)
    
    return { success: true, data }
  } catch (error) {
    if (error instanceof ApiError) {
      return { success: false, message: error.message }
    }
    return { success: false, message: '网络错误，请重试' }
  }
}
```

### 4.2 状态管理模板（含状态机设计）

```typescript
// 定义 UI 状态类型
type ItemUIState = 'disabled' | 'completed' | 'loading' | 'available'

function ItemCard({ item, onAction }) {
  const [isLoading, setIsLoading] = useState(false)
  const [isCompleted, setIsCompleted] = useState(false)

  // ========== 状态判断（集中定义） ==========
  const getUIState = (): ItemUIState => {
    if (item.status === 'disabled') return 'disabled'
    if (isCompleted) return 'completed'
    if (isLoading) return 'loading'
    return 'available'
  }

  const uiState = getUIState()
  const cannotAct = uiState !== 'available'

  // ========== 事件处理 ==========
  const handleAction = async () => {
    if (cannotAct) return
    setIsLoading(true)
    try {
      const result = await onAction(item.id)
      if (result.success) {
        setIsCompleted(true)
        wx.showToast({ title: '操作成功', icon: 'success' })
      } else {
        wx.showToast({ title: result.message || '操作失败', icon: 'none' })
      }
    } catch (error: any) {
      wx.showToast({ title: error.message || '操作失败', icon: 'none' })
    } finally {
      setIsLoading(false)
    }
  }

  // ========== 派生状态 ==========
  const buttonConfig = {
    disabled: { text: '不可用', bg: '#9ca3af' },
    completed: { text: '已完成', bg: '#10b981' },
    loading: { text: '处理中...', bg: primaryColor },
    available: { text: '立即操作', bg: primaryColor },
  }[uiState]

  // ========== 渲染 ==========
  return (
    <Button
      disabled={cannotAct}
      onClick={handleAction}
      style={{ 
        backgroundColor: buttonConfig.bg,
        opacity: cannotAct ? 0.5 : 1 
      }}
    >
      <Text>{buttonConfig.text}</Text>
    </Button>
  )
}
```
